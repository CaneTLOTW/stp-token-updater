# STP Token Updater – implementation review

Date: 2026-08-24
Current pre-release: v0.2.0
Current domain: `stp_token_updater`

This document records the repository review before live-system acceptance. The ordered acceptance plan is `CODEX_LIVE_HANDOFF.md`.

## Result

The original implementation was not install-ready. The repository has since been substantially reworked and anonymized. The visible product/UI/domain is now **STP Token Updater** (`STP = Sponsor Token Provider`). Provider-specific strings remain only where required by the upstream protocol, such as official source host, JWT claims and API fields/paths.

## Confirmed issues corrected

- missing/incorrect Config Flow auth handling in the initial prototype;
- incompatible positional `SensorEntityDescription` arguments;
- wrong Repairs issue-registry import;
- renewal checkpoint replay on every five-minute status poll;
- source failures not advancing source-check timing;
- definite auth/rate-limit API failures being hidden as generic verification failures;
- file/YAML-managed tokens incorrectly being treated as invalid solely due to source type;
- stale public product/domain naming;
- legacy custom-integration directory removed;
- runtime `strings.json` removed in favor of self-contained `translations/en.json` and `translations/de.json`;
- fixed English-only entity descriptions replaced with translation keys;
- runtime objects migrated to `ConfigEntry.runtime_data`;
- options flow moved to `OptionsFlowWithReload`;
- provider URL validation/normalization hardened;
- reconfigure and reauthentication separated;
- API/password authentication client hardened with one controlled password re-login;
- `429`/`Retry-After` modeled explicitly;
- token write verification constrained to one POST plus delayed readback;
- local HA brand icon added;
- tests expanded for scheduler, JWT, URL and write-safety boundaries;
- CI target aligned to Python 3.14.2 / Home Assistant 2026.8.2;
- `token_valid` now requires a future expiry plus authorized sponsor/name while still allowing a valid file-managed token to be considered valid.

## Current safety model

Automated tests must never issue a real sponsor-token write. The default is `dry_run=true`. A real write is reserved for one explicit acceptance operation and only when a freshly fetched candidate expires strictly later than the freshly observed active token.

A transport timeout after POST is treated as an uncertain write and followed by readback, not an immediate retry. Full JWTs and credentials must not be persisted or exposed.

## Known executable-test item

Rate-limit expiry/cleanup still needs focused testing with fake provider/source objects and controllable time. Specifically, verify that a due `Retry-After` resumes exactly the intended source/write operation, does not lose a pending apply intent, clears stale rate-limit metadata/Repair after resolution, and does not create a five-minute retry storm.

If reproducible, this should be fixed by Codex with a regression test before the live write stage.
