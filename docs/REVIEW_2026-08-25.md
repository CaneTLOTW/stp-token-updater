# Review after first live validation – 2026-08-25

## Overall result

The first live validation is convincing. The integration was installed in a real Home Assistant instance, survived a full Core restart, authenticated with API key and password/session, created all expected entities, persisted only sanitized metadata and did not send a sponsor-token POST because the current public candidate was not newer than the active token.

The Codex return report remains the primary evidence: `export/CODEX_STP_LIVE_VALIDATION.md`.

## Findings addressed in this follow-up

### Dashboard example used obsolete entity IDs

The original example still referenced short IDs such as `sensor.stp_token_status`. The real installation creates device-prefixed IDs such as `sensor.stp_token_updater_token_status`. `examples/dashboard.yaml` now uses the observed/default entity-ID scheme.

A compact Bubble Card example is additionally provided as `examples/bubble-card.yaml` for overview dashboards.

### CI generated excessive GitHub Actions noise

Three separate workflows were triggered on almost every push. During iterative development this created many redundant runs and failure notifications.

The repository now uses one consolidated `CI` workflow with:

- Tests, Hassfest and HACS as jobs in one workflow;
- path filters so README/docs/examples-only commits do not start CI;
- concurrency cancellation so a newer push supersedes an older run on the same ref.

### HACS update delivery / release discipline

For user-facing updates the integration should use semantic versions from `manifest.json` and GitHub Releases. HACS uses the latest GitHub Release tag as the remote version when releases are present.

The release workflow runs only after a successful CI run on `main`. It reads `manifest.json` and publishes `v<manifest version>` only if that GitHub Release does not already exist. Therefore every integration change intended for users must increment the manifest version. Documentation/example-only changes do not need a version bump.

## Remaining repository-metadata cleanup – manual GitHub setting

The GitHub repository metadata currently still contains the provider name in two places outside the Git tree:

- repository description: `Home Assistant integration for safe EVCC sponsor token monitoring and renewal.`
- topic: `evcc`

These values are stored as GitHub repository settings and are what link previews such as WhatsApp can expose. They are not controlled by README content.

Recommended replacement description:

`Home Assistant integration for safe sponsor/trial token monitoring and automatic renewal.`

Recommended topics:

- `home-assistant`
- `hacs`
- `home-automation`
- `sponsor-token`
- `token-renewal`

After changing the description, social-preview caches may continue showing the previous text temporarily.

## Force-update proposal – intentionally not implemented yet

The existing **Apply now** button correctly uses the same safety path as automation and refuses a candidate whose expiry is equal to or older than the active token. This is desirable for normal operation and must not be weakened.

If a real write-path acceptance test is still desired, add a separate advanced manual action rather than changing the existing button. Recommended constraints:

1. explicit name such as `Force re-apply current trial candidate`;
2. disabled by default behind an advanced option such as `allow_force_reapply`;
3. manual invocation only – never used by the automatic scheduler;
4. candidate must still be currently valid and must never be older than the active token;
5. all active Retry-After/rate-limit gates remain authoritative;
6. exactly one POST followed by the existing read-after-write verification;
7. transport timeout still means readback only, never blind repost;
8. dashboard control should use an explicit confirmation dialog;
9. action/result must be visible in `last_update_attempt`, `update_attempts` and diagnostics without exposing the token.

This is a v0.3-style feature rather than a reason to weaken v0.2 safety behavior.

The underlying password/session and single-401-relogin code paths are covered, so this is not considered a blocker for normal read-only operation, but should be checked when convenient.
